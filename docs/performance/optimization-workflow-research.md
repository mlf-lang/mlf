# MLF 性能优化研究与工程流程

2026 年 10 月 29 日

> **适用范围**：本文是后续性能研究与工程流程的建议，不是已启用的 CI 规则，也不替代或追溯修改 C4 既定实验协议。文中 C4 约 3% 的结果来自历史 P3 基线上的固定输入实验；**当前整合产物的性能收益未测**，不能据此声称 PR 整合后也快约 3%。
>
> 历史 P3 基线为 `875e483de49655030c4ffba1995b60610a50273a`，C4 实验候选为 `6be0c51f93ae8f31e4048aebe4c9a9bba3ce0a88`。本文不新增 benchmark 结果，建议中的门槛、预算和工具采用方式须在后续任务中单独评审。

## 结论与推荐

**对 MLF，最有效的流程不是把每个阶段都计时得更细，也不是把每个候选都完整长跑一遍，而是把探索与证明分开：先用低成本证据排除不值得做的方向，再把严格、独立的验证集中在少数有望进入生产的改动。**

建议采用两个相互连接的循环。

- **发现循环**：确认真实工作量 → 低扰动观测 → 提出能被证伪的成本解释 → 最小改动 → 定向正确性测试 → 廉价性能筛选。允许失败，也允许根据结果改假设；这些数据不承担最终收益声明。
- **确认循环**：冻结候选与协议 → 完整正确性资格 → 全新数据的配对分块实验 → 按效应、区间、适用范围与维护成本决策 → 对实际整合产物验证并设置回归门禁。结果不明确就保留“不明确”，不追加样本直到变显著。

这吸收了 Kalibera 与 Jones 的分层实验思想，以及 Harris 的“代码变化、资源变化、整体结果相互印证”方法，但以下具体门槛和排期是针对 MLF 的工程建议，不是论文已经证明的最优参数。[Kalibera 与 Jones 2013](https://kar.kent.ac.uk/33611/)，[Harris 2018](https://timharris.uk/misc/five-ways.pdf)

最应立即调整的是五件事：

1. **停止把精确 solver phase-wall 当成继续优化的前置条件。** 已有强迫求值和粗 IO 包装都显著改变产物或耗时，不能再把测量框架当主要产品。
2. **保留全部语义红线，但按阶段运行门禁。** 完整旧 oracle 和 raw-byte 比较不删；重复造控制程序、重复构建工具链、给早期低价值候选做正式长跑，可以减少。
3. **先解释分配的来源，不先假定 GC 是主瓶颈。** 历史 C4 研究的 P3 RTS 诊断显示 mutator CPU 为 73.584 秒、GC 为 12.823 秒；GC 约占该次总 CPU 的 14.84%。
4. **给 1% 与 3% 候选不同的证据预算。** 小收益并非不值得，但越小越容易被噪声淹没；维护面越大，需要的净收益和可迁移证据越强。
5. **同时经营小收益和大缺口。** 历史 C4 固定目标约为 GHC 的 10.59 倍，离 3 倍仍需约 3.53 倍整体加速。只靠等幅 3% 时间缩减，数学上约需 42 次复合改善，不能把这当可靠路线图。

本文不改变当前 C4 整合范围，也不要求为此次整合追加实验。流程建议面向后续研究，不应自动转化为现有 PR 的新门禁。

## 当前证据怎样改变优先级

历史证据来源为 C4 研究报告第 10 版、独立控制说明及两个 RTS 原始 stderr；这些材料已用于本文核对。C1、A/A、C2、C3 数值沿用既有研究摘要，本文未重新复核其全部原始样本。以下历史结果不是当前整合产物的复测结果。

仓库内的 [C4 实现与历史测量摘要](c4-local-transaction.md) 提供相关上下文；原始 cohort 与全部证据附件并未随本文纳入仓库。

| 既有结果 | 应保留的结论 | 不应推出的结论 |
|---|---|---|
| C1 首轮约 3.47%，追加 12 配对约 0.588%，区间含零且顺序方向相反 | 初筛效果可能回落；需要独立确认 | 已经可靠加速 3.47%；或已经证明完全无效 |
| A/A 约 ±4% | 原环境难以分辨小收益 | A/B 无偏；所有新环境都有相同误差 |
| C2 分配少约 1.17%，wall 慢约 1.53% | 降分配可能被排序或其他成本抵消 | allocation 是 wall 的替代指标 |
| C3 分配少约 1.84%，独立 wall 点改善约 1.07%，区间跨零 | 机制可能成立，但实际净收益未证实 | 已经获得可相加的 1.07% 收益 |
| C4 12 配对分成 6 block，点改善 2.996%，名义 95% 区间约 0.748% 至 5.194% | 历史固定产物与环境下的有条件正证据；两执行方向均改善 | 95% 至少快 2%；整个搜索过程的家族 95% 保证；其他机器或输入也快 3% |

历史 C4 候选新增 319 行，包含准入证明、局部构造与恢复、原路径回退等维护面。它与“十行微调获得 3%”不是同一决策。后续候选应把**长期双路径维护、测试负担和可撤销性**与收益一起列在候选卡上，而不是只列百分比；这不是重新裁决当前 C4 整合。

### 新增的 allocation 与 GC 诊断解读

原始诊断如下；每侧仅一次，且是 Main-only RTS 可观测 relink，不能作为普通 wall 的额外样本。

| 指标 | P3 | C4 |
|---|---:|---:|
| 累计分配字节 | 193,028,095,560 | 187,610,113,992 |
| GC 复制字节 | 10,997,091,320 | 10,891,959,768 |
| 最大 residency 字节 | 61,925,040 | 61,927,488 |
| MUT CPU 秒 | 73.584 | 72.315 |
| GC CPU 秒 | 12.823 | 12.823 |
| 总 CPU 秒 | 86.408 | 85.138 |
| GC elapsed 秒 | 12.828 | 12.828 |

193 GB 是整个运行期间的累计分配，不是同时驻留 193 GB。最大 residency 又不是进程树峰值 RSS，而且只在 major GC 等采样点观察，不能精确描述所有峰值。原日志的“%GC time 0.0%”与明细不一致，不能使用该字段；14.84% 是按 12.823 / 86.408 计算的诊断值。[GHC 9.14.1 RTS 统计说明](https://downloads.haskell.org/ghc/9.14.1/docs/users_guide/runtime_control.html)

**最合理的下一步假设是：大量短命结构的构造与遍历可能消耗了大量 mutator 工作；并非“GC 必然吃掉大部分时间”。** C4 少分配 2.807%，两次诊断的 GC 时间在输出精度内相同，也不能证明 GC 永不改善。它只说明 allocation 与 wall、GC 时间不是固定比例关系。先找重复构造、重复索引、重复分析及真正昂贵的数据形状，比盲调 heap 更有信息量。

### 监测器值得资格研究 但不能先认定它造成偏差

历史 C4 报告记录父进程每腿累计 CPU 中位约 10 秒，包含监测、准备、日志和等待线程等，且扫描工作目录的成本可能随样本积累增长。这是**共享 CPU、缓存或 I/O 竞争的潜在混杂线索**，不是“监测开销就是 10 秒 wall”，更不能从子进程时间减去父 CPU。

后续可在独立测量资格任务中，比较两种保持相同安全约束的监测实现：现有实现与固定扫描范围或增量计量实现。固定工作目录规模，记录父 CPU、子 CPU、子 wall 和资源压力；再测试目录增长是否改变处理顺序效应。只有真实干预结果才能支持因果判断。不能为了更好看的时间关闭资源保护，也不应用事后回归校正“修好”已完成 C4 数据。

## 不可变的测量与正确性契约

优化的是**完成同一项真实工作的普通产物耗时**。

- 主目标是固定 14 个 mlf-crates 模块的完整编译任务，每次重新推断 **544 fresh / 0 reused**；共用依赖允许复用。
- 目标推断缓存不得用来替代本次工作。工具链、依赖构建缓存与目标推断缓存必须分别命名、审计。
- checked 输出与独立 P3 参考的**原始字节**比较保留；哈希用于身份和转移校验，不能代替本次 raw-byte 比较。
- 保留作用域、刚性变量、错误优先级、惰性需求、异常需求顺序、rollback、公开状态结构，以及完整旧 oracle。
- P3 精确参考为 `875e483de49655030c4ffba1995b60610a50273a`。若后续以已整合版本为性能基线，同时保留原始 P3 作为语义参考；两个角色不能混用。
- 编译耗时目标与产物 runtime ≤2× C 是两条实验线。编译变快不证明生成程序变快；相同 checked 输出也不能替代所有目标后端的运行测试。
- 当前 MLF 与 GHC endpoint 存在差异：MLF 完成 checked MLF/xMLF crate，GHC 为目标 objects 的 `--make -no-link`。倍率是既定任务指标，不包装成同构后端的公平语言排名。

可以降低的是取得证据的重复劳动，不能降低契约本身。

## 可执行的分阶段 SOP

| 阶段 | 输入与最小输出 | 继续门槛 | 停止或转向条件 |
|---|---|---|---|
| 0 冻结问题 | 工作量、endpoint、基线、主指标、风险级别；一页契约 | 知道要省哪种真实工作 | 目标或“fresh”含义不清 |
| 1 准备可恢复实验环境 | 固定工具链与源、一次构建、依赖、旧 oracle、最小恢复包 | 身份与资源约束可复核 | 环境无法恢复或隔离 |
| 2 建立粗成本图 | 普通 whole-run wall/CPU；独立 RTS；已有 profile 与优化产物；形状分布 | 至少一个可检验瓶颈假设 | 只有父级 inclusive 热点名称 |
| 3 写候选卡 | 能省掉的操作、适用形状、净成本上界、语义义务、维护面 | 合理上界足以覆盖复杂度 | 即使全省也不值得 |
| 4 最小实现与筛选 | 定向独立控制、完整目标资格；固定小批普通运行 | 机制存在、正确、没有明显反向信号 | 机制未进入产物、语义失败、净成本更高 |
| 5 独立确认 | 候选冻结、完整旧 oracle、全新预声明 cohort | 区间、实际收益与风险同时可接受 | 预算耗尽仍不明确；不得追显著性 |
| 6 整合验证 | 实际整合 commit 的正确性、输出与针对性性能检查 | 没有交互回归，证据属于真实产物 | 单独候选收益未能保留 |
| 7 回归与复盘 | 稳定基线、分层 CI、失败样例、候选台账 | 获得可持续的小收益或新成本认识 | 测量与维护成本持续超过收益 |

### 阶段 1 只建一次可复用实验骨架

保留现在已经认证的 exact-child 计时和 MLF 特有审计，不为“采用成熟工具”再整体重写。把公共部分固化为一个版本化 runner 和一个离线 analyzer；候选仅填配置及必要的新控制。

准备成本、构建成本、诊断成本、普通采样成本、审查及证据归档成本分别记账。**性能研究的效率应看每个可信结果花了多少总时间，而不只看 benchmark 腿数。** 工具链和依赖允许安全复用，普通 A/B binaries 构建后不在每对样本间重建。相同源的确定性重复构建若产生相同字节，并没有增加布局样本。

先用现有历史数据估计哪一层最不稳定：连续运行、同一 session 的 block、环境重启，还是不同构建。不要机械套用“30 次足够”，也不要每个候选都重复昂贵的全层级 pilot。[分层实验与重复成本方法](https://kar.kent.ac.uk/33611/)

### 阶段 2 先问四个问题

1. **CPU 在忙什么，还是主要在等待？** 并列看子 wall、user/system CPU 和资源限制，而不是用 wall−CPU 当精确 I/O 时间。
2. **时间主要在 mutator 还是 GC？** 先读现有 RTS 明细，再决定是否值得堆分析或 GC 配置实验。
3. **优化后的普通代码里究竟还剩哪些工作？** 查看相关 Core、STG 或机器码中的循环、分配、dictionary、闭包、重复遍历；源码看起来消掉的工作不一定真的消掉。
4. **贵的是哪些形状，而不是哪种事件出现最多？** 将 graph 大小、fresh 数、component 大小、成功/失败路径、rebind 类型分层；计算“次数 × 代表性成本”的粗模型，不把 65.5% 准入率当成 65.5% CPU。

低开销采样先于侵入式 phase instrumentation。若可用，先检查 `perf stat/record` 的权限、符号与实际栈覆盖；GHC 的栈不能简单按普通 C 调用栈解释。已有 late-profile 可作为线索，不能把其百分比直接当 ordinary wall 分账。[GHC profiling 文档](https://downloads.haskell.org/ghc/9.14.1/docs/users_guide/profiling.html)，[GHC 工具作者关于系统 profiler 支持的说明](https://www.well-typed.com/blog/2022/05/hasura-supports-haskell-tooling/)

若某探针改变 demand、Core、接口优化，或令约 94 秒变成数百秒，应降级为“这个诊断版本的行为”，不要继续投入精力把它校正成真值。**阶段归因不精确，不妨碍通过语义等价干预和普通端到端实验验证候选。**

### 阶段 3 候选卡必须在写复杂实现之前完成

每张候选卡回答：

- 具体删除了什么工作？哪些必要工作完全没有删除？
- 在哪些可识别状态中生效？失败路径与不适用路径增加了什么成本？
- 是否只在同一次已认证操作内复用结果？跨状态复用如何失效？
- 有没有普通优化产物、输入分布或现有 trace 证明该工作真的存在？
- 什么观察会推翻假设？例如排序成本高于省下的更新成本。
- 涉及哪些 demand、first-error、scope、rigid、rollback 义务？
- 预计增加多少长期分支、重复实现、控制用例及维护负担？
- 正式确认最多愿意投入多少资源？证据不足时是延期、拒绝还是只作为重构？

优先级不是 profile 排名。可用一个定性决策式：**可信净收益 × 使用频率 × 可迁移程度 ÷ 实现、验证与维护成本**。不要把主观概率算成看似精确的小数；重点是显式暴露假设。

对新增复杂双路径的候选，必须有比“命中很多”更强的理由。对几行、局部、可撤销且没有新语义边界的改动，可接受较小收益；这不等于豁免正确性。

### 阶段 4 廉价筛选不是小型正式论文

建议一个候选的初筛默认只用 **1 至 2 个平衡 block，即 4 至 8 次普通完整目标执行**，再加必要的独立机制诊断。这个数量是工作预算，不是统计保证。

顺序是：静态义务审查 → 最小定向测试 → 正确性资格 → 检查普通产物 → 小批端到端筛选。每个完整目标仍保留 544/0 与原字节门禁。先用便宜控制淘汰错误实现；正式确认前再对冻结候选运行完整旧 oracle 与全部新增控制。

初筛只决定“值不值得继续”，不发表显著性。没有看到 1% 收益不能宣布没有 1% 收益；但若候选复杂、机制成本上界很小、初筛无信号，就可以因工程价值不足而停止。停止的理由应是**机会成本**，不是伪造统计等效。

### 阶段 5 正式确认只使用全新数据

候选、编译参数、普通 executable、依赖、主指标、实际意义阈值、样本数、顺序方案、环境中断规则及异常处理，在第一条正式样本前冻结。任何实质代码修改都生成新候选，不能保留“有利的旧样本”。

默认采用简单的固定样本量方案。预先平衡并随机化 ABBA 与 BAAB 等时间 block；不要先跑完所有 A 再跑 B。每个 block 含同数 A/B，每侧都做完整 fresh 目标；block 的真实执行顺序必须记录。具体样本量由 pilot 方差与最低值得识别的效应决定，见技术附录。

- 主分析用预先选定的配对 log-ratio 或其他明确 estimand；不能看到结果后在均值、中位数、最佳值和几何均值之间挑赢家。
- GHC 锚点是绝对目标和环境线索，不是自动去噪器。9 秒 GHC 与 90 多秒 MLF 对环境的响应可能不同。
- 同时报告时间序列、block 效应、AB/BA 方向、普通 CPU 与诊断 allocation；辅助指标不替换主 wall。
- 预声明允许的基础设施故障和失效条件。候选超时、内存超限或语义错误不能当作“离群值”删除后补一个好样本。
- 区间跨零就是不明确；区间不跨零也不代表达到工程意义门槛。完成既定窗口后停止，不追显著性。

### 阶段 6 与 7 不让收益在整合后消失

独立候选百分比不能相加。如果多个改动都作用于同一成本，合并后的收益往往重叠；若需要解释交互，可另开基线、X、Y、X+Y 的小型因子实验。应将这种额外的交互研究与既定整合验证分开，不把单独候选的历史结果当作组合产物的新结果。

回归门禁分三层：

- **每次相关提交**：确定性语义控制、完整保留的旧 oracle 对照、关键非平凡形状、fresh/raw-byte 资格，以及少量稳定的优化产物断言。
- **性能敏感提交的专门任务**：固定目标的普通 A/B；可信 allocation 或指令计数作为早期告警，不能自动替代 wall。
- **稳定环境的定期趋势**：固定工具链/硬件分层保存时间序列。阈值要来自本环境历史方差，告警后用新 A/B 复核；不要让共享云机一次 1% 抖动直接阻断所有 PR。

LLVM LNT 适合在已有持续性能数据后做长期跟踪；现在不必先部署一个服务。先把现有 runner 的原始 JSON 和一张趋势图做可靠，再决定是否接入。[LLVM LNT 官方文档](https://llvm.org/docs/lnt/tests.html)

## 正确性如何分层而不缩水

完整 oracle 的独立性比“又新增了多少测试行”重要。期望结果由冻结 P3、独立规范或手写固定 fixture 得到，不能通过候选 helper 计算后再与候选比较。

推荐把测试矩阵按义务而不是按函数名组织：

- **成功路径**：shared 与 unshared、fresh 连 old、未变化 fresh 后代、不同 component 大小、binder 不变与改变。
- **拒绝路径**：scope escape、rigid、kind 不合、缺失节点、冲突别名、计数器边界和非法 prepared 驱动。
- **顺序与事务**：多步 trace、前一步改变状态、失败前后公开状态、rollback、第一错误。
- **惰性需求**：Name/Kind 等 payload 的受控 bottom/异常探针；区分应触发与不应触发的需求。有限测试不证明所有部分值等价。
- **物理表示义务**：凡公开契约要求的树形、counter、alias、写回顺序必须保留；内部可变的 index 树形只按其明确不变量验收。
- **非空洞性**：统计成功/拒绝、非平凡 sharing、实际进入新路径和回退路径的数量。不能由候选的成功谓词筛出“容易通过”的测试集。

QuickCheck 原论文恰好研究了 unification：普通随机项加“统一成功”的前提，会严重偏向简单变量情况；论文也发现规范自身的错误。对 MLF，生成器覆盖和前置条件正确性应成为门禁，而不是把通过次数当安全程度。[QuickCheck 原论文第 5.1 节](https://www.cs.tufts.edu/~nr/cs257/archive/john-hughes/quick.pdf)

差分、property 与 metamorphic 测试互补。保持 scope 的重命名可验证等变关系，但重命名后的诊断文本不能要求与原文本逐字节相同；应比较明确定义的变换关系。EMI 的“未执行代码删除”也不能直接套到类型推断器：运行时未执行的表达式仍可能被类型检查，删除它可能改变可接受性、错误或推断结果。[EMI 原论文](https://www.vuminhle.com/pdf/pldi14-emi.pdf)

## 成熟工具的采用边界

| 工作 | 优先复用 | MLF 仍必须自己负责的部分 |
|---|---|---|
| 普通命令计时 | 已认证的 exact-child runner；必要时以 hyperfine 作简便探索 | fresh 工作量、依赖边界、原字节比较、resource guard、分块随机计划 |
| 统计计算 | R 的 t.test、qt、p.adjust；或相应成熟统计库 | estimand、独立单位、顺序与异常规则、预声明、候选选择史 |
| 采样与系统诊断 | perf、GHC RTS、已有 late-profile | GHC 栈/符号适配，测量扰动资格，普通与诊断产物分离 |
| 优化产物检查 | GHC dump；少量 inspection-testing 断言 | 断言哪些机制必须存在或消失，而非锁死整个 Core 文本 |
| 语义测试 | QuickCheck 等现成框架，冻结 oracle | 生成器、部分值观察、scope/rigid/rollback 规范 |
| 长期趋势 | 原始 JSON 加脚本起步；必要时 LNT | 噪声预算、基线版本、回归决策与复核 |

没有必要为每个候选重新实现 t 分布 CDF、分位数求根、bootstrap 或统计报告器。保留独立核算，但可由一条很短的第二实现调用成熟库，并用固定合成数据检查符号、配对和区间变换。**独立性不是重复造全部基础设施。** 数据导入先拒绝缺失、重复与非有限值，避免统计库自动丢弃坏样本。[R t.test](https://stat.ethz.ch/R-manual/R-devel/library/stats/html/t.test.html)，[R p.adjust](https://stat.ethz.ch/R-manual/R-devel/library/stats/html/p.adjust.html)

hyperfine 可快速重复外部命令并导出 JSON，但默认重复、预热、shell 和统计行为随版本而异；不能未经适配就替换当前正式协议，更不能让预热命中目标推断缓存。不要复制文档中的 root 级清缓存或机器调优操作到共享环境。[hyperfine 官方项目](https://github.com/sharkdp/hyperfine)

inspection-testing 可把“没有某中间类型/调用/分配”等优化承诺变成检查；这比每次人工翻整份 Core 更可持续。但产物属性既不保证端到端更快，也不证明语义正确。[Breitner 2018](https://arxiv.org/abs/1803.07130)

## 资源与恢复协议

1. **隔离研究与生产工作区**。不同候选用独立源码与输出目录，保护 refs；重构建和 benchmark 在团队内串行协调。
2. **每条运行有不可混淆的身份**。保存源、工具链、binary、工作量、环境、实际顺序、开始/结束/exit/中断状态以及原始 stdout/stderr。
3. **计时外做准备和验证**。不过“在计时外”不代表可以与下一条计时并行争资源；上传、压缩、目录遍历应在 block 间完成。
4. **恢复包分层**。稳定工具链与依赖单独保存；每个 block 只 checkpoint 小型增量和 receipts，结束后统一完整证据包。不要每次重传大缓存。
5. **保留现有资源上限**。变更监测实现必须先证明保护不变；不能以低噪声为由关闭内存、磁盘或进程树检查。
6. **环境重置就是证据边界**。新 boot、不同 CPU 或工具链进入新 cohort，记录层级；不要把残余样本无标记拼接。若一次执行的结果未知，先检查状态和已有证据，不能盲重跑。
7. **保留失败与否定结果**。候选台账写机制、成本、失败原因、有效范围和最后决定，减少下一轮重走 C1/C2/C3 弯路。

## 下一轮最值得做的三个小闭环

**第一优先是整理已有证据，不再启动大框架。** 将现有普通 timing、RTS、optimized dump 和图形状计数整理成一张成本地图，明确“已经知道”“只有代理指标”“完全未知”。上述历史 RTS 的 mutator/GC 分解已经能排除“193 GB 所以先调 GC”这种过快判断。

**第二优先是测量资格与复用。** 找出 runner 中随历史文件增长的工作，评估固定扫描域或增量预算的可行性；只提出保持同等安全约束的最小变更。把工具链恢复、主/诊断产物区分、raw-byte 检查和统计脚本固化为可复用组件，而非重做一次实验平台。

**第三优先是候选成本上界。** 在区分其他独立优化方向及其证据的前提下，研究剩余 mutator 工作：同一操作内是否重复计算 component、scope 或 permission 信息；哪些 persistent 中间结构构造后立刻丢弃；哪些昂贵形状被当前快速路径排除。只读证据不足时先补一个能改变决策的观测，不立即写几百行新事务路径。

历史 C4 窗口作为已完成的实验保留，不追加相同目标样本争显著性。后续异输入正确性与适用边界验证、新候选的独立确认、实际整合产物的性能测量，是不同目的的工作；本文不新增这三类验证或测量的结果。

## 技术附录一 统计设计与决策规则

### 先写清估计什么

“整体 14 模块任务的耗时”是主工作量。14 个固定模块不是 14 个独立随机样本，544 个推断组也不是 544 个独立 timing 样本。不能用它们虚增 n。

设同一 block 内有两对 A/B 普通运行。可预声明：

`d_j = 0.5 × [log(B_j1/A_j1) + log(B_j2/A_j2)]`

`theta = mean(d_j)`，`R = exp(theta)`，时间改善 `g = 1 − R`。

若 block 差值可近似独立且误差模型适合，先对 theta 做区间，再指数变换；theta 区间 [L,U] 对应改善区间 [1−exp(U), 1−exp(L)]。这是**分块配对几何时间比**，不是算术平均时间之比，也不是中位数之比。若产品真正关心预计总等待秒数，可把算术均值差或比设为主 estimand，但应在运行前选择。

Kalibera/Jones 的主要方法处理分层随机效应与均值之比，其技术报告明确说没有直接处理 paired comparisons。这里的配对 block 设计是针对云端时间漂移的工程选择，不能冒称原论文已替 MLF 验证了这个模型。[2013 技术报告及 2020 arXiv 存档](https://arxiv.org/abs/2007.10899)

### 顺序平衡不等于无偏

ABBA/BAAB 能减弱某些平滑漂移，但不能保证消掉缓存 carryover、温度、宿主争用或累积目录规模的影响。应保存实际时间顺序，画 A/B 原值及 block 效应图；检查方向分裂、持续趋势和 session 差异。

若出现明显相关性，不能只把所有腿扔进普通 t-test 或逐腿 bootstrap。优先改善设计、增加真正独立的 session/block，或收窄声明。仅有 6 个 block 时，靠“自相关检验没有显著”不能证明独立，复杂 mixed model 或 bootstrap 也不会凭空产生信息。

A/A 是管线与噪声诊断，不是 A/B 无偏证书。布局、环境与新路径可能交互，A/A 根本没有施加这种改变。对当前固定部署 binaries 的条件比较仍有工程意义；需要区分它与“算法在不同构建、机器或布局上普遍更快”的声明。[Mytkowicz 等 2009](https://research.ibm.com/publications/producing-wrong-data-without-doing-anything-obviously-wrong)，[Stabilizer 2013](https://people.cs.umass.edu/~emery/pubs/stabilizer-asplos13.pdf)

### 需要多少重复

粗略规划可用：

`n ≈ (1.96 + 0.84)^2 × sigma_d^2 / delta^2`

其中 n 是**独立分析单位**数量，sigma_d 是该单位 log-ratio 的标准差，delta 是希望以约 80% power 识别的真实 log-ratio 差异的量级。下表用百分比近似 log 差，仅用于预算。

| 独立单位的标准差 | 识别约 1% | 识别约 2% | 识别约 3% |
|---|---:|---:|---:|
| 2% | 32 | 8 | 4 |
| 4% | 126 | 32 | 14 |

这些是正态近似，不是建议拿 4 个 block 就做强声明。小样本 t 临界值、方差估计不准、自相关、多个 session 和多重检验会提高所需量；规划时应留余量。若主单位是 4 腿 block，32 个单位就是 128 次完整编译，不是 32 腿。

不要根据赢家的观测效应做事后 power 来证明样本足够。用独立 pilot 或历史同设计的方差，按**值得检测的最小效果**规划。若一个约 1% 候选要花过多资源才能区分，而更有上限的方向尚未检查，暂缓它是合理选择，不等于证明它无效。

### 显著 有用 等效 与不劣是四件事

- “有正证据”：改善区间下界大于 0。
- “至少达到 δ”：改善区间下界大于 δ；仅点估计超过 δ 不够。
- “实际等效”：先选可接受差异范围，例如时间比 [0.99,1.01]，再检查适当等效检验。对两个单侧 α=0.05 的 TOST，对应 90% 双侧区间完全落入预声明范围；95% 区间包含 0 不能证明等效。
- “不劣于 ε”：时间比的合适单侧上界低于 1+ε；这是重构或简化可能需要的决策，不是“已加速”。

Schuirmann 的原研究来自生物等效统计；这里借用的是检验逻辑，不借用任何领域阈值。依赖结构仍须按正确分析单位处理。[Schuirmann 1987](https://pubmed.ncbi.nlm.nih.gov/3450848/)

建议将低风险小改动与复杂双路径分级，在候选卡上分别声明最低值得接受的点收益、允许回归上界和必须具备的解释证据。可以从“小而局部约 0.5% 至 1%；新复杂路径约 2% 至 3%”作为讨论起点，但不能追溯修改 C4 已冻结门槛，也不应把这些数值机械化为长期规则。

### 筛选偏差 多重比较 与停止

探索期间允许试很多想法，但不能把赢家的探索区间作为最终区间。冻结唯一候选后，用独立新数据确认，可避免把探索噪声直接带进效果估计；前提是没有看过确认数据再改候选或分析。共享同一环境的持续偏差并不会因为“数据新”就消失。

如果一个研究周期确认多个候选，仍需区分**每候选**保证与**整个周期**保证。固定一组比较可用 Holm；持续开新候选可预分配总和不超过目标 α 的预算，或只做明确的单次条件声明，不宣称全搜索 95%。不要隐去失败候选。[R 官方多重检验说明及 Holm 原文索引](https://stat.ethz.ch/R-manual/R-devel/library/stats/html/p.adjust.html)

最简单的停止规则是固定 N 和预算，结束后判“通过、拒绝、不明确”。若必须中途作统计决定，需预先设计 group-sequential 或 confidence sequence。普通 95% CI 每轮查看、第一次排除零就停，不再具有普通固定样本含义。Howard 等提供 anytime-valid 方法，但它们依赖明确的概率条件；不能把任意受相关云噪声影响的 wall 数据直接代入一个公式。[Howard 等 2021](https://arxiv.org/abs/1810.08240)

**对目前 MLF 的建议仍是固定 N，暂不自建序贯统计平台。**

## 技术附录二 热点与成本模型

对一个真正互斥的成本部分，若其占总时间比例 p，局部加速 s，则理想整体加速为：

`S = 1 / [(1−p) + p/s]`

这是有边界的估算，不是对未来收益的证明。历史 instantiation 27.9% 与 unify 18% 是 inclusive 视角，可能嵌套，不能相加。即使假设某个真实互斥部分占 28%，彻底消除它的整体上限也仅约 1.39 倍；它单独无法填补按历史 C4 倍率计算的约 3.53 倍缺口。[Amdahl 1967](https://doi.org/10.1145/1465482.1465560)

对候选更实用的模型是：

`节省 ≈ Σ(形状 k 的次数 × 实际删掉的单位成本) − 新增准入成本 − 失败回退额外成本`

把它写成范围，不要伪精确。样例 replay 或 microbenchmark 要保留真实输入形状与求值契约，不能把已强制求值的数据测成“推断变快”；它们用于验证局部解释，不代替完整目标。计数本身可能改变严格性、优化和执行，因此形状计数保持为独立诊断通道。

三种证据应相互校验：

1. **机制证据**：普通产物确实不再执行相关构造/遍历。
2. **资源证据**：按预期减少分配、指令或其他可解释工作。
3. **任务证据**：普通、完整、fresh 工作量的 wall 改善。

三者不一致时，应修正解释，而不是选择最好看的指标。资源下降但 wall 不变，可以是次要成本、抵消、带宽或环境效应；不能自动认定任何一种原因。

### 定位与解释

**Curtsinger Berger 2015**

*Coz Finding Code that Counts with Causal Profiling*，SOSP。DOI [10.1145/2815400.2815409](https://doi.org/10.1145/2815400.2815409)；[会议原文](https://www.sigops.org/s/conferences/sosp/2015/current/2015-Monterey/printable/090-curtsinger.pdf)。核对 virtual speedup、progress point 与实现/评价。它通过暂停其他线程测试潜在局部加速对进度的影响；论文报告平均约 17% 开销，不能称为“几乎无扰动”。评价没有验证 GHC 适配。本项目借其因果问题，不直接推荐移植工具。

**Sansom Peyton Jones 1997**

*Formally Based Profiling for Higher-Order Functional Languages*，TOPLAS；[作者机构全文](https://www.microsoft.com/en-us/research/wp-content/uploads/1997/01/profiling-toplas.pdf)。早期版本发表于 POPL 1995。核对成本归属语义及优化跨 SCC 边界讨论。非严格语言中成本归属需要明确语义；现代 GHC 的具体行为仍以 9.14.1 官方文档为准。

**Breitner 2018**

*A Promise Checked Is a Promise Kept Inspection Testing*；[arXiv:1803.07130](https://arxiv.org/abs/1803.07130)。核对 Core 属性、融合示例与插件接口。可将非功能性优化承诺放进测试，适合减少反复人工审阅；不能证明整个程序更快或所有语义等价。

**Harris 2018**

*Five Ways Not to Fool Yourself*；[作者文章](https://timharris.uk/misc/five-ways.pdf)。核对五个方法，尤其实际工作量、轻量正确性、资源指标与逐步走向生产设置。是一手工程方法文章，不是统计功效定理；其中硬件控制建议要按共享云环境权限与代表性取舍。

**Scherer 2026 草稿**

*How to Benchmark the Measure Explain Test Improve Loop*；[INRIA 作者草稿](https://cambium.inria.fr/~scherer/drafts/how-to-benchmark-2026.pdf)。核对第 3 至 5 节。其有价值之处是要求检验性能解释并迭代修正 benchmark。该稿不是已核实的同行评审结果；其中偏重最佳时间或对低噪声的宽松表述，不作为 MLF 1% 至 3% 收益的确认规则。

### 语义与回归

**Claessen Hughes 2000**

*QuickCheck A Lightweight Tool for Random Testing of Haskell Programs*，ICFP。DOI [10.1145/351240.351266](https://doi.org/10.1145/351240.351266)；[原文](https://www.cs.tufts.edu/~nr/cs257/archive/john-hughes/quick.pdf)。核对第 2.4 与 5.1 节。unification 案例特别支持检查生成器与非平凡覆盖，避免条件过滤产生虚假安全感；不是“随机测试可证明 MLF 正确”。

**Yang Chen Eide Regehr 2011**

*Finding and Understanding Bugs in C Compilers*，PLDI。DOI [10.1145/1993498.1993532](https://doi.org/10.1145/1993498.1993532)；[作者研究组记录](https://www.flux.utah.edu/paper/yang-pldi11)；[原文](https://web.stanford.edu/class/cs343/resources/finding-bugs-compilers.pdf)。核对差分测试与生成安全机制。应借鉴“先保证输入和观察有确定含义，再比较实现”的原则；Csmith 本身不是 MLF generator，也不覆盖 MLF 的部分值需求和首错语义。

**Le Afshari Su 2014**

*Compiler Validation via Equivalence Modulo Inputs*，PLDI。DOI [10.1145/2594291.2594334](https://doi.org/10.1145/2594291.2594334)；[作者全文](https://www.vuminhle.com/pdf/pldi14-emi.pdf)。核对 EMI 定义、覆盖收集和剪枝算法。适合启发受约束 metamorphic testing；不能把仅对某些运行输入等价，误当成类型推断行为、错误或原始输出普遍等价。

**SIGPLAN 2018 官方方法清单**

[Empirical Evaluation Guidelines](https://www.sigplan.org/Resources/EmpiricalEvaluation/)。强调声明范围、合理基准与证据判断；清单是辅助判断，不是勾满即可信，也不是每个候选都要套同一昂贵流程。

## 最后的判断

**当前最值得优化的，不仅是 MLF 的几段代码，也是从想法到可信收益的周转时间。**

正确性约束应保持强；探索期的行政和测量成本应降低；正式收益声明应使用新的、预声明的数据。把节省下来的时间投入能改变决策的观测、非平凡语义覆盖和更有成本上限的候选，才有机会在积累小收益的同时接近 3 倍 GHC 的目标。
