优化前基线与第一项优化决策

2026 年 10 月 26 日  |  PR25 aa11ffd 与已批准本地修复

结论

同一批 14 个源模块、依赖已编译并复用、目标推断缓存全冷时，普通 MLF 编译中位数为 163.896307032 s；GHC 9.14.1 plain -O2 的中位数为 9.047647972 s。当前比例为 18.114797 倍，尚未达到不超过 3 倍的目标。达标阈值是 27.142943916 s，意味着还需约 6.04 倍加速，减少约 83.44% 的普通 wall time。

第一项优化应从命名空间成员选择开始

late cost-centre profile 中，Bootstrap.Module 的 partialSelectItem 与 selectType 在四个互不重叠的 CCS 上下文中占 38.4513% sampled CPU、44.0067% profiled allocation。直接归属于这些选择器的 Map 分配为 127.280 GB，占全部 Map-exclusive 分配的 71.4565%。主要 Map 热点不能简单归因于 solver。

建议先测 parent filter before union：先按父实体筛选成员，再 union 与去重，避免每个成员选择都构造完整 visible interface。必须保持实体排序、alias 去重、成员可见性、歧义与缺失名称错误、循环导出 fixed point、Abstract 成员惰性和全部独立检查。此处是有证据的候选，不是已验证收益。

本报告在任何性能优化代码修改之前形成。forced phase wall 与 late CPU profile 用于定位，不用来替代普通基线。GHC 输出优化后的 native objects，而 MLF 输出经独立检查的 xMLF crate 并写入 query cache；两者完成的产品不同。

阅读顺序：第 1 至 2 节界定基线与诊断扰动；第 3 至 7 节解释热点和验证门槛；附录给出阶段数值和复现证据。GB 为十进制 10^9 bytes，MiB 为 2^20 bytes。

1 比较范围与普通基线

计时从新子进程启动到退出。准备依赖、复制输入、哈希校验和 benchmark harness 的前后检查不计入编译 wall time；编译进程内必要的解析、推断、检查与目标输出计入。没有执行完整 74 模块 native bootstrap，本报告也不作该范围的性能或语义结论。

控制条件

GHC 命令核心为 --make -no-link -j1 -O2 -XHaskell2010，固定 package db、显式 package 和 source roots；plain 依赖也用匹配的 plain flags 预编译后复用。MLF producer 按仓库的 -O2 与 demand-preserving flags 构建，运行 --compile-crate，使用全新的目标 queries 目录，复用冻结的依赖 crate 与 Prelude。

共同环境固定 GHC_ENVIRONMENT=-、LC_ALL=C.UTF-8、OMP_NUM_THREADS=1、OPENBLAS_NUM_THREADS=1、MAKEFLAGS=-j1；普通样本 GHCRTS 为空。任务控制的重负载串行运行，但没有 CPU affinity 或独占物理宿主保证。OS cache 未清空；这里的 cold 指目标推断结果全冷，不是冷页缓存。

宿主快照为 Linux 6.18.55 x86_64、AMD EPYC 9V74，约 9.7 GiB 物理内存、无 swap。cgroup 控制未挂载，额外的宿主资源 cap 未知。资源守护上限为单进程 6 GiB address space、进程树 5 GiB RSS；宿主可用内存下限 3 GiB、磁盘余量下限 4 GiB、输出增长上限 8 GiB、wall 上限 6 小时。

统计范围

每组 3 个样本只描述当前宿主。MLF 范围为 163.331291426–170.168008194 s，MAD 为 0.565015606 s；plain GHC 范围为 8.453523167–9.532567807 s。没有据此建立置信区间或跨机器推广。历史 128.58 s / 5.67 s 的命令与 revision 未独立核验，未合并入基线。

第 1 次 MLF 普通样本早于 CPU/rusage 仪表加入，CPU 数据缺失，未回填估算；其输入、544/0 计数和产物字节一致性已独立后验核对。

4 复合阶段不能按名字直接下结论

module resolve 包含命名空间与导出工作

module.resolve 的 51.682578694 s 是强制 resolved crate 结果的复合区间，覆盖 module resolution、导入导出环境与 fixed-point 导出处理等被该结果 demand 的工作。late CCS 独立证实大量 selector 成本落在 settleExports 和 exportsFor 路径；两种证据相互解释，但不能把 sampled CPU shares 换算为这里的 wall 秒数。

cache write publish 不只是文件写入

cache.write-publish 的 exclusive 为 23.019529905 s，inclusive 为 28.157811578 s。嵌套 query.cache.encode 的 5.137713778 s 已单独记账并从父 exclusive 扣除。父级还包含 writeFile、参数与 UTF-8 处理，以及外部 /bin/mv 的 fork、exec、wait。runtime/mlf_system.h 的 os_runProcess 使用 10 ms polling；不是 supervisor 的 5 ms loop。

forced 版本的大 heap 可能放大 fork 成本，所以这不是“普通缓存写入要 23 秒”的证据。既不能把该标签全部归为磁盘吞吐，也不能把 fixed polling interval 乘以 544 当作已经测出的实际等待总量。需要后续在普通实现中拆分发布路径，才能判断优化空间。

crate assemble validate 不等于独立 checker

crate.assemble-validate 的 exclusive 为 12.222363884 s，inclusive 为 17.667390839 s。它包括最终 resolvedExports 再次执行 exportsFor、exports 去重、依赖 semantic hash、layout / reachability / bindings / protection、makeObject 与 validateInterface，以及所选 CrateObject 和 QueryReport 的 deep force。延迟的 GroupResult semantic hash 也可在这里被 demand。

嵌套 payload fingerprint 与 encode 的 5.445025443 s 已从此父 exclusive 扣除。把剩余 12.222 s 叫作“类型检查器成本”会误导优化。late profile 中可识别的独立 checker 根只有约 1.55% sampled CPU；它不是当前首要目标，也不授权减弱检查。

forcing 边界已检查 但不承诺普通求值顺序

PhaseSelfTest、ForceSelfTest 与区间解析控制均通过；optimized Core 中 opaque purePhase / purePhaseOnce 的 value 参数在 helper 边界保持 lazy，forceAction 在 IO 中执行所选 forcing。该证据检查 helper 优化行为，不是对所有 callsite 普通 demand 的普遍证明。强制指定输出本来就会改变 demand 和 retention。

具体 demand 边界也已逐处复核：Constraint 的 incremental 输入 graph 在 prepare 外强制，费用归 constraints.generate；SourcePlan 只 force 选定输出，不触碰未使用的 legacy lowering；TypeContext memo 的 demand 仍留在 evidence / elaboration；String forcing 不强制 lazy index；solver 跳过未使用的 ScopeIndex jump memo。这些是诊断边界约束，不是普通求值顺序的等价证明。

原始 RTS before/after snapshot 可用于审计，但 GC 更新的计数器不能当成精确 per-phase allocation 或 phase-end retained heap。

5 Late CPU profile 指向的实际热点

完整解析 81,682 个最终 CCS 行；exclusive 整数总和精确等于 318,156 ticks 与 431,827,326,224 allocated bytes。实际 header 为 1,000 µs/tick；-i0.005 是 heap profiling interval 参数，不是 time-profiler tick 请求，不能据此换算 CPU 样本。20 个 flat exact 行和全部 inherited 百分比在输出舍入范围内对得上。

7 验证结论与下一步门槛

已经建立的事实

输入 provenance audit 核验了 2,581 个唯一 pinned 文件，涵盖真实 GHC binary、launcher、settings、toolchain、installed dependencies、resolved source modules、host/configuration inputs、14 个冻结源模块、GHC objects 与 MLF dependency artifacts。profile 完成后的再次审计也全部通过。哈希校验约 1.259 GB 输入；这证明输入来源一致，不是独立的完整语义测试。

普通 MLF 三次、RTS、forced 与 late-profile 目标编译均成功，544 fresh / 0 reused；.mlfci 和 .mlfco 与先前参考输出逐字节一致。GHC 普通样本确认恰好编译 14 模块且依赖对象没有改变。此处没有绕过独立 xMLF 检查。

第一项候选的验证门槛

• 先保留并发布本报告、冻结输入与原始数据，再改变性能代码；不把诊断 instrumentation 当作优化。

• 只实施 parent filter before union 的最小改动；保持 entity identity、排序、alias 去重、错误与 lazy Abstract 语义。优先利用现有 selector 语义，不更换 hash 或跳过 checks。

• 覆盖显式成员列表、全部成员、Abstract、重复 alias、歧义/缺失名称、成员可见性、导出循环与 fixed point 的正反例；保留模块与 crate 的独立验证。

• 同一 frozen14 冷目标重编译必须仍为 544/0，并比较完整产物字节、query semantic fingerprint 与错误行为；随后运行授权范围内更广的回归测试。

• 在没有 profiler 的普通 executable 上重新独立计时，至少使用与基线相同的样本数、环境和资源守护；依据普通 median 验收收益，同时报告 allocation / RSS 是否回退。

• 只有普通 MLF median ≤ 27.142943916 s 才在本宿主本输入上达到目标。一次局部改动不能预先保证整体 6.04 倍加速。

后续候选与不做的事情

第二优先级是 solver instantiation 中重复 index/map 构建与 projection/restoration；第三是不可变 serialization / fingerprint 共享；第四是在一次 compile 内复用已认证依赖快照。20 个 fingerprint 根合计 36,344 ticks、55.591 GB；两处依赖加载分别为 3,725 / 3,756 ticks、各约 6.262 GB。都需要代码与数据身份论证及普通计时，不采用弱 hash、过期缓存或减少检查来换速度。
