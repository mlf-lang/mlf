# Graph54 read fusion: bounded experiment

Semantic/raw gates pass. Foundation has mixed pairs; Async, Frontend and Xmlf each have two timing pairs favoring C, with higher RSS. Frontend and Xmlf show larger RSS costs than Async. None establishes stable gain or merge evidence.

Baseline commit: `fc300bc9fdc389b585cbef0630fc8915d53e89c5`.
The patch mechanically unfolds 54 fully saturated internal calls in 34 functions of Bootstrap.Graph to the original readSTArray RHS. Public readDense signature/body/arity, all writes and primitives remain unchanged. Arguments are single identifiers used once; no new strictness, pragma, algorithm or representation. The reversible byte proof and independent source review preceded execution.

The real Graph corpus uses actual Graph/Solver, not an extracted wrapper. Its host adaptation preserves the repository GraphDense corpus and four-line expected output. Main adds 14 silent state/demand cases, including shared action across writes, ignored-result bounds errors, payload laziness, array/index/low demand and signed Int64 wrap. Both baseline/candidate passed O0/O2 with 16 modules each. This is selected coverage, not a universal runtime proof.

Ordinary code shows genuine local fusion with **+8432 bytes (+2.4343%) .text**. Conditional denseContains closure accounting drops 352→176 bytes on the specified fresh successful path; this is not measured heap allocation or savings. Other paths already fused or retain offset boxes. Full 95-module candidate Graph.o is byte-identical to the independently inspected single-object result.

One fixed Foundation 15 **C-A-A-C** window completed with four fresh query caches. Every leg matched original A raw CI/CO and ordered 532 groups / 539 members / 14 owners; whole-query byte comparison is an additional observation. Two pairs point in opposite directions; first A has elevated system time, with unknown cause. No sample was dropped, adjusted or followed by additional samples. See JSON for wall, CPU, user-only and RSS arithmetic. No stable benefit, significance, general regression or merge conclusion follows; no selective retries or added samples. No comparison with profiling/E-counter timings. Native/fixedpoint remains paused.

A separate fixed **Async 5 A-C-C-A** window compiled the complete `mlf-async/0.3.0/library` crate without executing its task/process APIs. It reused the same ordinary A/C compilers and existing Foundation/builtin interfaces. All four legs matched the new original A raw CI/CO and ordered **86 groups / 87 members / 4 owners**; the fifth module is an import/reexport facade. Both wall-time pairs favored C: C/A **0.913955 / 0.938011**, geometric ratio **0.925905** (a descriptive **7.4095%** reduction). CPU also decreased in both pairs, while maximum RSS increased by **2.4127% / 2.5980%**. Four fresh query caches do not imply cold OS caches. These two pairs are a workload-specific signal, not stable/significant benefit, measured heap-allocation savings or whole-compiler qualification. Foundation remains mixed; the workloads are not pooled. See `results/async-acca.json` for all four unadjusted samples.

A separate fixed **Frontend 11 C-A-A-C** window compiled the complete `mlf-frontend/0.3.0/library` crate with no entry point, reusing the same ordinary A/C compilers and original Foundation/Core/builtin interfaces. All four legs matched the original A raw CI/CO and ordered **763 groups / 858 members (849 values and 9 instances) / 11 owners**. Both wall-time pairs favored C: **7.4009% / 7.0029%** lower, with a descriptive geometric reduction of **7.2021%**. Total CPU was **7.1437%** lower geometrically, but system time was **16.0108%** higher and maximum RSS increased in both pairs (**7.8628% / 7.6811%**, geometric **7.7719%**). That observed RSS cost is larger than Async's **2.5053%** geometric increase; RSS is not allocation volume, and these observations do not identify the cause. All four unadjusted samples, 11 source hashes and reused dependency hashes are in `results/frontend-caac.json`. Each leg passed the raw/ordered gates before its sample was accepted and the next leg began. These are two descriptive pairs, not stable or significant improvement, allocation savings or merge evidence. Foundation, Async and Frontend remain separate results, with no pooled estimate.

A separate fixed **Xmlf 6 C-A-A-C** window compiled the complete `mlf-xmlf/0.3.0/library` crate with no entry point, using the same ordinary A/C compilers and existing Foundation/Frontend/Core/builtin interfaces. Each leg matched the original A raw CI/CO and complete ordered **173 groups / 207 value members / 6 owners** before its sample was accepted and the next leg began. Both wall-time pairs favored C, but by quite different amounts: **1.9800% / 10.2692%**, with a descriptive geometric reduction of **6.2161%**. Total CPU was **6.2842%** lower geometrically; system time was **26.0202%** higher geometrically, with opposite directions across the two pairs. Maximum RSS rose in both pairs (**8.3456% / 8.2270%**, geometric **8.2862%**), not evidence of lower allocation. A3 was **6.4113%** slower than A2 in wall time and **6.4259%** in CPU; all four samples are retained unchanged, without assigning a cause or adding samples. Qualification timing is excluded. Full samples, six source hashes and reused dependency hashes are in `results/xmlf-caac.json`. These remain two descriptive workload-specific pairs, not stable/significant improvement or merge evidence. Foundation remains mixed, and no Xmlf/Frontend/Async/Foundation pooled estimate is made. This window includes no next workload or native/fixed-point step.

A separate **two-call Frontend RTS memory diagnostic** ran newly relinked ordinary A-stats then C-stats once each, with baked `-s` and fresh query caches. Both matched the original raw CI/CO and ordered **763 / 858 / 11** reference. Managed allocation was **8.4986%** lower and copied bytes **4.8858%** lower, while major-GC-sampled maximum live bytes rose **6.8343%**, RTS memory **4.9505%**, and process maximum RSS **4.8659%**. Maximum live residency had **84 / 79 major-GC samples**, not a continuous or matched-schedule peak trace. Lower allocation volume can coexist with higher sampled live data and RSS; these different metrics do not establish the cause of the earlier RSS cost. This is one fixed diagnostic A-C sequence with **zero performance samples**, not another performance pair or an addition to the previous C-A-A-C window. New link layouts and statistics output also distinguish these producers from the original timing binaries. All counters, raw statistics text and diagnostic wait4 values are retained in `results/frontend-rts-diagnostic.json` without a timing gain calculation. The literal **0.0% GC** fields are retained: [GHC 9.14.1's non-threaded report path](https://github.com/ghc/ghc/blob/ghc-9.14.1-release/rts/Stats.c#L1379) performs integer division before printing those percentages. They do **not** mean zero GC; the generation and GC-time rows are nonzero. No corrected percentage replaces the reported value. The reported **0 MiB fragmentation** is a limited whole-MiB aggregate, not proof of zero allocator slack, pinned-object or OS-level fragmentation; maximum slop is separate. RTS memory and process RSS maxima need not be simultaneous and should not be subtracted to partition memory.

Experimental branch: `perf/main-baseline-gap-20261114`, directory `tools/performance/main-baseline-gap-20261114/graph54-read-fusion`. This is an experimental result, not evidence for merging into main or for native/fixed-point qualification.
