# Stage18: exact nominal owners captured by a recursive function

The opt-in shared-source route can now capture an ordinary owner of an already
admitted, closed, parameter-free DATA or SUM declaration in its existing single
monomorphic recursive function. This extends source replay and planning only.
Runtime C/H, packet ABI, allocator, placement and fault defaults remain Stage17.

## Contract and bounds

A capture is the existing ordinary `Reference`, with its full nominal identity,
Type, Down/below support and original Access. The implementation neither forces
the owner nor projects its fields to manufacture captures. A nominal identity is
the exact declaration index, name and source path, not a matching field layout.
The selected canonical declaration must already occur in the freshly published
DATA/SUM inventory. Classifying a capture cannot silently add another family
or admit unrelated compiler dictionary declarations afterward.

A nonempty nominal inventory selects
`closed-scalar-callable-nominal-shared-view-captures/1`. Sorted rows contain the
original binder, complete type, exact declaration index and occurrence paths;
this policy also includes a callable array, even when empty. The ordinary free
owners partition exactly into disjoint scalar, callable and nominal categories.
Complete lexical shared-view pairs stay separate. When nominal captures are
absent, earlier evidence and generated bytes remain unchanged.

The total capture bound remains 64, including used self and every full view.
SUM arm factories retain their separate 32-external-capture bound. The recursive
knot and original annotation applications keep the existing same-home Hole/Fill
and checked publication rules. No stricter support, E0 label, expected Code or
shared type vector is invented from a nominal type.

Still outside this slice: open/parameterized/foreign nominal types, nominal
Scheme arguments or generic captures, ordinary arrows containing nominal leaves,
recursive DATA fields, cross-family or callable SUM fields, bare/partial shared
views, arbitrary recursive values, and generic/mutual recursion. Existing DATA
and finite self-family SUM restrictions continue to apply.

## Two genuine checked sources

Both original compiler invocations succeeded and their diagnostic source custody
and checked projection passed. The frozen older transport then rejected each
nominal external capture before native execution. Those complete original
artifacts and rejections are preserved. New replay subsequently completed full
custody, projection and normalization for both actual checked terms; it did not
substitute a guessed AST or reconstruct a binder from a name hint.

- DATA owner: a pending annotated Payload contains a pending `addInt 20 1` and
  a separately annotated `sharedId : Int -> Int` field. The recursive function
  captures only the original box owner. It does not acquire a fabricated direct
  recursive shared view from the callable field's type.
- SUM owner: a pending annotated IntList seed contains a pending computation of 21 and an ordinary
  application `(lambda n -> Cons n Nil) 123` as its tail. The recursive function
  captures that exact seed owner plus its genuine complete shared Int view.
  The unused tail application and body remain unentered. The ready scalar 123 may be
  allocated; non-demand is not the absence of allocation.

Both call the same recursive closure on Nil, then Cons/Cons/Nil and return 42.
Initial Nil completes before nominal-owner or bonus demand and shared Int
invocation. View acquisition and allocation may happen earlier. Two Cons
activations share the original owner and one bonus evaluation/memo, while the
same original shared node/body is invoked at Bool/Int/Int.

For DATA, source/metadata/emitted code establish projection through the original
fields, retain before end-borrow and before container drop, and preservation of
the callable field's complete Int view. Runtime projection, memo, callback and
handoff events corroborate the corresponding owners. Individual retain,
end-borrow/drop operations and every restored owner's Access field are not
separately event-traced; the tests do not claim such a trace.

## Local validation

Transport: 190 focused checks pass; broad module regression: 342 passes with three
pre-existing optional artifact-dependent skips. The combined planner suite
passes 108 tests with no skips, including five older native fragments. Coverage
includes distinct same-shaped declarations and same-typed owners, nested and
unselected occurrences, exact partition/type/declaration/support forgeries,
64/65 total captures and the separate 32/33 SUM external limit.

All eight source/placement/O0-O2 native conditions pass, with complete O0/O2 report
equality per case/mode. The original DATA/coarse/O0 pair was revalidated and
reused; only seven missing pairs were launched. Across them, 256 copied-report
and 80 copied-structure controls reject changed owners, fields, views, Code,
eager/duplicate demand, pending memo targets, budgets and ledger corruption.

One fixed DATA/coarse fuel 29 pair was selected from the actual generated tick
schedule before launch: 24 entry operations through Fill plus five generic-body
operations; the next drop attempts 30. Both faults retain the same filled live
cycle at fault 4. Default retain leaves 5,824 bytes; explicit terminal destruction
retires exactly 5,824 bytes with identical category accounting and the same fault.
This is not rollback. There was no threshold search or target retry.

Four O0 ASan/UBSan conditions pass with LSan off. Their eight process records
complete with exit 0, empty stderr and no cleanup errors; full reports match
ordinary runs including every work field. 128 report and 40 structure controls
also pass. Fourteen prior source-program conditions were freshly replayed,
planned, checked and emitted, matching Stage17's complete plans/resources and
four generated files. Their actual native reports were reused, not relaunched.
All 13 production C/H files and the public driver remain identical to Stage17.

The final portable suite builds two fresh ordinary producers and runs both
sources through CLI/replay/planning/native execution. Both return Int42 with
seven zero terminal ledgers. Their complete native reports equal the retained
coarse O0 reports. All 16 recorded outer/build/capture/compile/run processes
finish with exit 0 and no cleanup errors; 64 report and 20 structural controls
pass. Outer durations 114.17 and 116.10 seconds include compiler work and are
not runtime benchmarks. No additional fault pair is run.

The unchanged work cap is 67,108,864. DATA coarse/groups uses 54,242,537/53,681,504;
SUM uses 66,097,184/65,742,987. SUM is close to the bound, so this does not establish
larger or deeper recursion support. Requested peak bytes are 21,224/20,128 and
22,560/21,776 respectively, not RSS. No work fields are ignored and these source
qualification runs are not performance benchmarks.

## Reproduce

```sh
T=tools/experimental/resource-native/tests
python3 -B "$T/test_module_shared_transport.py"
python3 -B "$T/test_planner_v8_nominal_captures.py"
python3 -B "$T/test_source_v8_nominal_captures.py" \
  --ghc /absolute/path/to/ghc-9.14.1 --cc cc \
  --output /absolute/new/nominal-capture-source-output
```

The portable source runner performs exactly two fresh coarse source/CLI/native
cases and no additional fault pair. Optional retained-capture roots enable host
replay/golden tests separately; a stored capture is not native admission.

CI keeps the existing 26-case, 60-minute source job unchanged. The two new
nominal-capture cases run in a separate 20-minute job with the same official,
checksum-pinned GHC installation and existing per-process limits. This adds
setup cost on a separate runner instead of extending the long serial pipeline.
The new planner suite is also run by the existing fragment job. Both source
jobs retain logs and artifacts on failure. Exact-head CI remains necessary
after publication; local qualification does not establish its future outcome.

This remains an experimental bounded source route, not a general MLF source
bridge, default-runtime change, full GC replacement or Perceus comparison.
